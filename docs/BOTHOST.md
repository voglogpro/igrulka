# BotHost: постоянный игровой сервер

Подготовлено для Node.js 24. Развёртывание на аккаунте пользователя ещё не выполнено: нужны доступ к панели и назначенный HTTPS-домен. Telegram-бот, токен BotFather и SSH-туннели игровому процессу не нужны. Если форма BotHost требует токен, уточните у поддержки создание обычного веб-сервиса с кастомным Dockerfile; не создавайте фиктивного бота ради формы.

## Подключение репозитория

1. Подключите `https://github.com/voglogpro/igrulka` и согласованную опубликованную ветку/ревизию.
2. В дополнительных настройках включите собственный корневой `Dockerfile` и домен. Получите автоматический `*.bothost.tech` либо настройте свой домен по инструкции платформы.
3. Укажите внутренний порт `8080` и переменные ниже. HTTP-обёртка платформы не нужна: сервер уже реализован в Node.
4. Выполните deploy. Откройте HTTPS `/healthz`, затем `/api/server-info`. Первый должен вернуть только `{"ok":true}`, второй — явно заданный публичный адрес и `status:ready`.
5. Откройте игру, создайте co-op комнату, отправьте приглашение другу, оба подтвердите готовность, хозяин нажимает старт. Проверьте публичный WSS `/match`, четыре штаба и команды обоих игроков. До этой проверки совместимость реального reverse proxy BotHost с долгоживущим WSS не считается подтверждённой.

| Переменная   | Значение                                                                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| `PUBLIC_URL` | Обязательно: `https://ваш-домен` — origin без пути, credentials, query и fragment                                     |
| `PORT`       | `8080`, должен совпадать с внутренним портом панели                                                                   |
| `HOST`       | `0.0.0.0`                                                                                                             |
| `CLIENT_URL` | Необязательно: `https://voglogpro.github.io/igrulka/releases/8.12.1/`; без значения клиент отдаётся с игрового домена |
| `MAX_ROOMS`  | `2` по умолчанию; допустимо 1..16, поднимать только после нагрузки                                                    |

`PUBLIC_URL` никогда не вычисляется из Host/X-Forwarded-Host. TLS завершается на reverse proxy платформы; контейнер принимает HTTP/1.1 и WebSocket Upgrade. Существующий протокол, delta-снимки и negotiated permessage-deflate используются без отдельного прокси-процесса. Конфигурация не меняет локальный `server/index.mjs` и internet launcher.

## Контейнер и проверка локально

```sh
docker build -t skyfront-hosted .
docker run --rm -p 8080:8080 -e PUBLIC_URL=https://game.example skyfront-hosted
```

Или Node 24 без Docker, предварительно `npm ci` и `npm run build`:

```sh
PUBLIC_URL=https://game.example PORT=8080 node server/hosted.mjs
node --test tests/unit/hosted-server.test.mjs
```

В PowerShell переменные задаются отдельно:

```powershell
$env:PUBLIC_URL = 'https://game.example'
$env:PORT = '8080'
npm.cmd run multiplayer:hosted
```

Dockerfile собирает portable HTML в build stage; runtime устанавливает только production-зависимости и работает как `node`, одним процессом. Runtime находится в `/usr/src/skyfront`: официальный bind mount `/app` не должен скрыть собранные файлы. Переменные окружения не запекаются в образ. `/healthz` не перечисляет комнаты и игроков. SIGTERM/SIGINT закрывают собственные соединения и сервер.

Комнаты живут в памяти: restart/deploy прерывает матч, автоматического восстановления серверного матча с диска нет. Не включайте несколько реплик без маршрутизации комнат и общей модели состояния. Клиентская solo-кампания остаётся отдельным браузерным сохранением.

## Хватит ли 2 ГБ

Графика, аудио и WebGL работают у игроков, не в Node-контейнере. 2 ГБ — лимит памяти контейнера, а не гарантия количества армий, комнат или FPS. Для игры двух друзей начинайте с одной комнаты (`MAX_ROOMS=1`), затем оценивайте RSS, CPU, задержку тика и очередь снимков под реальной нагрузкой. Одна симуляция использует основной JS-поток: четыре vCPU не превращают её автоматически в четыре параллельных симуляции.

Локальный allocation baseline Node 24.18.0/Windows: настоящий RoomServer — RSS 64,1 МиБ без комнаты и 65,2 МиБ после создания co-op с четырьмя фракциями и 500 пехотинцами. Это размещение объектов без активного боя и длительного обмена снимками, не оценка пикового потребления Linux-контейнера и не гарантия вместимости 2 ГБ. Нужен отдельный длительный нагрузочный замер.

Дополнительный реальный WS-прогон 8.11 (состояние 19): четыре города, 480 наземных единиц и 10/20/100/400 летящих аппаратов, два клиента с задержкой подтверждения 500/1200 мс, по 12 секунд на случай. Пиковый RSS общего процесса сервера и двух Node-клиентов — 271,6 МиБ. Нулевые отключения и паузы, максимум один ожидающий снимок. Это короткий локальный активный бой с искусственным начальным составом, не длительный Linux-тест и не обещание такого же CPU/FPS на тарифе. Отчёт — `artifacts/qa/network-load811.json`.

Лимиты RAM/CPU и распределение ресурсов между проектами сверяйте в панели. При превышении RAM процесс может быть убит (код137), матч потеряется. Сборка с dev-зависимостями тоже требует памяти; runtime использует готовую сборку. Docker CLI в среде этой проверки отсутствовал: Node entrypoint, HTTP и WebSocket проверены нативно; сборку и запуск образа требуется выполнить на платформе.

## Первичные источники и непроверенные условия

- [Домены и порты](https://bothost.ru/docs/domains-and-ports): `0.0.0.0`, переменная PORT, внутренний порт.
- [Веб-приложения и домены](https://bothost.ru/docs/web-apps-domains): HTTPS на443, reverse proxy, свой HTTP-сервер, автоматический и собственный домен.
- [Кастомный Dockerfile](https://bothost.ru/docs/custom-dockerfile): собственный образ/entrypoint, Node-пример, предупреждение о mount `/app` и размещении build-артефактов вне него. Node24 задаётся нашим образом, а не обещается стандартным autodetect платформы.
- [Память и лимиты](https://bothost.ru/docs/bot-memory-timeout-rate-limits): лимит Pro2ГБ, OOM/restarts.
- [Тарифы](https://bothost.ru/): текущие цены, vCPU и память.

В просмотренных официальных документах не найдено явного SLA для WebSocket Upgrade, idle timeout и длительности матчей. Нужен реальный WSS smoke на выданном домене и, если есть ограничение, подтверждение поддержки. Само наличие HTTPS-домена этого не доказывает. Платные ресурсы и аккаунты этой подготовкой не создаются.
